# Plugged
Draw Belgian (AREI) electrical schemas in the browser: eendraadschema, situatieschema, bedradingsschema (wiring diagram), your own symbols, rule verification and vector PDF export.

Spring Boot 4 backend (Java 21, JPA, file-based H2) with a React 18 + Vite frontend. The built frontend is served by the backend, so a production install is a single jar.

## Quick start
| You want to | Command | Open |
|---|---|---|
| Develop | `cd backend && mvn spring-boot:run`, and in a second terminal `cd frontend && npm i && npm run dev` | http://localhost:5173 (proxies `/api` to the backend) |
| Run as one jar | `cd backend && mvn clean install`, then `PLUGGED_ADMIN_EMAIL=you@example.be java -jar target/plugged-*.jar` | http://localhost:8080 |
| Run with Docker | `PLUGGED_ADMIN_EMAIL=you@example.be docker compose up --build` | http://localhost:8080 |
| Build a Docker image with the version of the pom | `./docker-build.sh` (makes `plugged:<version>`, `plugged:<major.minor>` and `plugged:latest`) | |
| Run as a program on one computer (no server, no account) | `desktop/jpackage.sh`, then install what it made (see [Desktop program](#desktop-program-one-computer)) | opens by itself |

On the first start Plugged asks for the details of the administrator account and a **setup key** that it prints in its log (the console; `docker compose logs plugged` in Docker), see [Accounts and signing in](#accounts-and-signing-in).

Requirements: JDK 21 and Maven 3.9+. Node is only needed for frontend development (`mvn clean install` downloads Node 22 into `frontend/node` by itself). Docker is optional.

## Changing the port
| What | Default | How to change it |
|---|---|---|
| Backend / jar | 8080 | `PORT=9090` (or `SERVER_PORT=9090`) as environment variable, or `--server.port=9090` on the command line |
| Vite dev server | 5173 | `DEV_PORT=3000` |
| Port the dev server proxies `/api` to | 8080 | `BACKEND_PORT=9090` (must match the backend port) |
| Docker Compose (host side) | 8080 | `PLUGGED_PORT=9090` in the shell or in a `.env` file next to `docker-compose.yml` |

Examples:
```
# jar
PORT=9090 java -jar backend/target/plugged-0.1.0.jar
java -jar backend/target/plugged-0.1.0.jar --server.port=9090

# development: backend on 9090, frontend on 3000
cd backend && mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=9090
cd frontend && DEV_PORT=3000 BACKEND_PORT=9090 npm run dev

# Docker
PLUGGED_PORT=9090 docker compose up --build      # then open http://localhost:9090
docker run -p 9090:8080 -v plugged-data:/data plugged
```
Windows PowerShell: set the variable first, e.g. `$env:PORT=9090; java -jar ...`.

To make a port permanent without environment variables:
- Backend: put `server.port=9090` in `backend/config/application.properties` (Spring Boot reads `./config/application.properties` from the working directory; the folder is git-ignored). It works for `mvn spring-boot:run` from `backend/` and for the jar when started from that folder.
- Frontend dev server: put `DEV_PORT=3000` and `BACKEND_PORT=9090` in `frontend/.env.local` (git-ignored, works on every OS).
- Docker Compose: put `PLUGGED_PORT=9090` in `.env`.
- Docker without Compose: the container listens on `PORT` (8080 by default); either map another host port (`-p 9090:8080`) or change both (`-e PORT=9090 -p 9090:9090`).

## Data
Every project is saved as one JSON document (with its owner and the groups it is shared with) in a file-based H2 database: `backend/data/plugged` when you run from `backend/`, the `plugged-data` volume (`/data`) in Docker. Override the location with `SPRING_DATASOURCE_URL` (e.g. `jdbc:h2:file:/some/dir/plugged`). The symbols are stored in the same database: the standard ones shared by everybody, the own ones per user or group. Use **JSON ↑ / JSON ↓** in the header to export and import a project file.

## Offerte (price lists)
A professional user keeps what he pays for his material in **price lists** (Account › **Prijzen**, `features/pricing/PricingPanel.jsx`; stored by the server as JSON owned by the editor, `pricing/PriceListService`, `GET/POST/PUT/DELETE /api/price-lists`). A list is his own; he can share it with his groups (their members use it and can copy it, only the owner changes it; a save names its version, 409 when it changed since). A new list (`model/pricing.js`, `newPriceList`) already has the usual articles without prices: mechanisms, centre plates and rockers, cover frames of 1 to 4 places horizontal and vertical, flush boxes, light and appliance points, XVB/VOB cables, breakers, differentials, boards. Parts of a price list:
- **Artikels**: code, description, kind, unit (piece or metre), purchase price excl. VAT and labour minutes. A cable article names its designation (`XVB 3G2,5`, compared without spaces, fire class or `mm²`), a protection article its kind and specs (`2P B16`, `2P 40A 30mA`; what it leaves out matches anything).
- **Symbolen**: what one element is made of (a socket: mechanism + centre plate; a double socket: twice that) and how many **places** it takes in a cover frame (0 for a light point or appliance). A waterproof element can have its own articles (`type|h`).
- **Afdekramen**: the frame for 1 to 5 places, horizontal and vertical, and the flush box (one per place).
- **Arbeid, marge, btw**: hourly rate, margin on material, default VAT (21 %, 6 % renovation, 0 % reverse charge) and validity; **Bedrijf**: name, address, VAT number, IBAN, contact, logo (scaled to 600 px), introduction and terms.

On the **situatieschema** a symbol has a **Montage** (horizontal, the default, or vertical), and several selected symbols can be **combined in one cover frame** (`item.combo`, one direction per combination). Neither is drawn; both only count for the offerte.

**Project › Offerte** (`features/quote/QuoteDialog.jsx`, worked out in `model/quote.js`) counts the elements of the eendraadschema (as the materiaallijst does) with their articles, one frame per element or combination for the sum of its places in its direction (elements that are not on the plan: a horizontal frame of their own), the flush boxes, the protective devices and cable lengths of the materiaallijst (rounded up to whole metres), the labour (minutes of all articles at the hourly rate, rounded up to a quarter of an hour), extra lines (keuring, travel, ...), margin and VAT. What cannot be priced is listed, not left out: an element without articles, an article without a price, a frame for more places than the list has, a cable or protective device without an article, a circuit without a cable length. The details of the offerte (number, date, client and site from Kaderinfo, VAT, margin, extra lines) are kept in the project (`project.quote`). It downloads as a **PDF** (`features/quote/quoteExport.js`, A4 with logo, company, client, lines by kind, totals and the VAT mention) and as an **Excel** workbook with amounts in euro.

## Offline and installable (PWA)
Plugged is a Progressive Web App: Chrome, Edge and Safari offer to **install** it (a window of its own, an icon on the desktop, the home screen of a phone or tablet), and it keeps working **without a connection** once it was used online.
- The service worker (`frontend/src/offline/sw.js`, written by the build as `/sw.js` with the list of files of that build, see `vite.config.js`) stores the application itself at installation. The calls of the API that read (who is signed in, the symbols, the project list, the projects) go to the network first; their last answer is kept, so without a connection the last known state opens. Signing out empties that store (another person may use the browser next).
- A **save without a connection** is kept on the device (IndexedDB, `offline/offlineStore.js`), per user and project, and the top bar shows *Offline* or *Wacht op verbinding: n* (a click tries again). It is sent as soon as the browser says the connection is back, and every 30 s while something waits (`offline/sync.js`, `hooks/useOffline.js`); the work of the device that did not reach the server yet opens first on the next start. A project that somebody else saved in the meantime is never overwritten: the work of the device becomes a new project *“<name> (offline <date>)”* and the user is told.
- The manifest is `frontend/public/manifest.webmanifest`, the icons are in `frontend/public/icons` (source: `icon.svg`).
- On Android the installed PWA is the app; iOS adds it to the home screen from Safari (Share › Add to Home Screen). The service worker needs HTTPS (or `localhost`), so a server behind a reverse proxy with a certificate.

## Desktop program (one computer)
For somebody who works alone (an independent electrician): Plugged as a program with its own Java, no server to install, no account to make. `desktop/jpackage.sh` builds it with `jpackage` (JDK 21) on the system it runs on: a `.tar.gz` (and a `.deb` when `dpkg-deb` and `fakeroot` are installed) on Linux, a `.zip` (and an `.msi` with the WiX toolset) on Windows with `desktop\jpackage.cmd` (double-click it; it runs `desktop\jpackage.ps1`, add `-NoBuild` to pack the jar that is already built), a `.dmg` on macOS (not signed: the first time open it with right-click › Open). The workflow `.github/workflows/desktop.yml` builds all three on GitHub.

**Versions and releases.** The version of Plugged is written in one place only: `<version>` in `backend/pom.xml` (three numbers, the first at least 1, e.g. `1.2.0`). The jar (`plugged-<version>.jar`), the installers, the MCP server and the tests take it from there. To publish a release, raise that version and push it to `main` (or `master`): every push there lets the workflow check the version, and for a version without a release it builds the installers on Windows, macOS and Linux, and publishes them as release `v<version>` with the tag on that commit. Other pushes, and pom changes that keep the version, publish nothing. *Run workflow* (by hand) builds the installers of any branch as downloads of the run, without a release, to try them first. Raise the last number for fixes, the middle one for new features, the first one for big changes.
- The program (`desktop/DesktopLauncher`, started with `--desktop`, profile `desktop`) listens on **127.0.0.1 only**, on port 47800 (or the next free one), and keeps its data (database, logs) in the user's folder: `%LOCALAPPDATA%\Plugged` on Windows, `~/Library/Application Support/Plugged` on macOS, `~/.local/share/plugged` on Linux; `PLUGGED_HOME` overrides it.
- At the first start it makes one local account (the administrator, with the name of the user of the computer). It opens the browser signed in with a link that works once and only for 5 minutes; there is no sign-in screen and no *Afmelden*. A small window shows that Plugged runs, with *Openen in de browser*, *Gegevensmap* and *Stoppen*. Starting the program again while it runs only opens the browser (the second start asks the first one, with the secret of `instance.properties` in the data folder).
- Requests for another host name than 127.0.0.1 / localhost are refused (421), so a web page elsewhere cannot reach the local server by pointing its own domain name at 127.0.0.1. Registration is off and the contact form of the Info page is hidden.
- **No QR codes**: a QR code opens the schema on the server, and nobody can reach this computer to scan one. The editor has no QR item, no Alt+Q, no QR button in the project list and no QR step in the tour; the Info page leaves it out and has its own first paragraph, and one FAQ entry says why. The API of the QR codes (`/api/public/**`, `/api/projects/{id}/qr-key`) answers 404 (`DesktopHostFilter`).
- It is the same jar as the server (`java -jar plugged-<version>.jar --desktop` does the same), and as a PWA it also works offline in the browser.

## AI link (your own assistant draws)
Plugged has no AI of its own and sends nothing to one. Instead a user connects **his own** AI assistant (Claude, ChatGPT, Claude Code, ...) to his Plugged account, and the assistant works in Plugged as him, for instance to turn the floor plan of an architect (PDF, photo) into a situatieschema with the electrical points marked per circuit. Account › **AI-assistent** shows the address to give the assistant, the steps, a skill for the assistant to download (`features/ai/skill.md`), the connections (each can be ended) and personal keys.
- **MCP** (Model Context Protocol, Streamable HTTP): `POST /mcp` (`ai/McpController`), one JSON-RPC message per request, plain JSON answers, no sessions. The tools (`ai/McpTools`, descriptions in `resources/ai/tools.json`): `plugged_guide` (how to draw, `resources/ai/guide.md`), `list_projects`, `get_project`, `list_symbols`, `create_project` (from `resources/ai/new-project-<language>.json`, kept equal to the new project of the editor by `src/test/ai/newProjectTemplates.test.js`), `draw_floor_plan` and `save_project`. Every tool works with exactly the rights of the user (ProjectService, SymbolService); every save keeps the previous version in the history. A student in educational mode cannot use it.
- **draw_floor_plan** (`ai/PlanDrawer`) draws floors described in real metres the way the templates do: rectangular rooms (shared walls merged, the name with the floor area), extra walls, doors, windows, passages, texts and the symbols with their marks (`B4`). It picks the largest standard scale that fits (or keeps the scale of a project that already has drawings) and centres the plan. With marks it sets `pending.generateOneWire` in the project: when the user opens it (the assistant gives the link `/?project=<id>`), the situatieschema opens with *Eendraadschema maken*.
- **Signing in** (OAuth 2.1, `ai/AiAuthService`, `ai/AiAuthController`): an unauthenticated call to `/mcp` answers 401 with `WWW-Authenticate: Bearer resource_metadata=...`; `/.well-known/oauth-protected-resource/mcp` (RFC 9728) and `/.well-known/oauth-authorization-server` (RFC 8414) describe the rest. Assistants register themselves (`POST /oauth/register`, RFC 7591; https addresses, or http on the loopback address on any port for Claude Code), the user agrees on `/oauth/authorize` (a page of the editor, after signing in: it shows which assistant and where it goes back to), PKCE S256 is required, the code works once for 2 minutes. Access keys last 1 hour, refresh keys 60 days and rotate (a refresh key used twice ends its connection). Personal keys (30, 90 or 365 days) are for assistants set up with a fixed `Authorization: Bearer` key. Only SHA-256 hashes of keys are stored; a new password, a temporary password from an administrator and removing the account end every key of the user. A request with an `Origin` of another site is refused.
- **Settings**: `PLUGGED_PUBLIC_URL` (`plugged.public-url`): the address the assistants use, e.g. `https://plugged.example.be` (else the address of the request, behind a proxy from its `X-Forwarded-*` headers). Claude.ai, Claude Desktop and ChatGPT connect from the internet: Plugged must be reachable there over HTTPS (a reverse proxy with a certificate); Claude Code also reaches a Plugged on the same computer or network (the desktop program, too).
- Connecting: in Claude, Settings › Connectors › Add custom connector with `https://<your Plugged>/mcp`; in Claude Code `claude mcp add --transport http plugged https://<your Plugged>/mcp`.

## Accounts and signing in
Everybody signs in before the editor opens (Spring Security, session cookie, CSRF token in the `XSRF-TOKEN` cookie / `X-XSRF-TOKEN` header).

| Setting | Environment variable | What it does |
|---|---|---|
| `plugged.admin.email` | `PLUGGED_ADMIN_EMAIL` | Email address of the administrator, **required**. It is also the address the contact form of the Info page writes to (it replaces the former `PLUGGED_CONTACT_EMAIL`). |
| `server.servlet.session.timeout` | `PLUGGED_SESSION_TIMEOUT` | How long a session lasts without any request (default `8h`). |
| `plugged.setup.key` | `PLUGGED_SETUP_KEY` | The setup key of the first start. Empty (default): a new random key at every start, printed in the log until the administrator exists. Set it only for automated installations. |
| `plugged.auth.max-failed-logins` / `plugged.auth.lockout` | `PLUGGED_MAX_FAILED_LOGINS` / `PLUGGED_LOCKOUT` | After this many wrong passwords in a row (default `5`) an account is locked for this long (default `15m`). |
| `plugged.auth.ip-max-attempts` / `plugged.auth.ip-window` | `PLUGGED_IP_MAX_ATTEMPTS` / `PLUGGED_IP_WINDOW` | At most this many failed sign-ins, first starts and registrations per network address (default `30`) per window (default `15m`); then 429. |
| `plugged.max-request-size` | `PLUGGED_MAX_REQUEST_SIZE` | Largest request body of the API, e.g. a project (default `5MB`); larger ones get 413. |
| `plugged.max-projects-per-user` | `PLUGGED_MAX_PROJECTS_PER_USER` | How many projects one user may own, the trash included (default `500`, `0` = no limit). |
| `plugged.project-history` | `PLUGGED_PROJECT_HISTORY` | How many saved versions of every project are kept as its history (default `50`, `0` = no history). |
| `plugged.trash-days` | `PLUGGED_TRASH_DAYS` | How many days a deleted project stays in the trash before it is removed for good (default `30`, `0` = never). |
| `plugged.presence-timeout` | `PLUGGED_PRESENCE_TIMEOUT` | After how long without a heartbeat an open editor no longer counts as present (default `90s`). |
| `server.forward-headers-strategy` | `PLUGGED_FORWARD_HEADERS` | `native` (default): behind a reverse proxy that terminates HTTPS (nginx, Traefik, Caddy), its `X-Forwarded-*` headers are trusted from internal addresses, so requests count as HTTPS (Secure cookies, HSTS) and the sign-in limits see the real visitor. Without a proxy nothing changes. `none` turns it off. |
| `server.servlet.session.cookie.secure` | `PLUGGED_SECURE_COOKIES` | `true` forces the Secure flag on the session cookie. Leave `false` (default) for a local setup over plain `http://localhost`. |
| `plugged.content-security-policy` | `PLUGGED_CSP` | The Content-Security-Policy header (default: only the own scripts, styles, images and API; no framing). Empty = no header. |

- **First start**: as long as there is no administrator, the page shows *Welkom bij Plugged* and asks for the **setup key**, the first name, surname and password of the administrator. The setup key is printed in the log of the server at every start (a new one each time) as long as there is no administrator, so only somebody who can read the log of the server can become the administrator, not whoever opens the page first. The email address is the one of `PLUGGED_ADMIN_EMAIL`, shown read-only: it cannot be chosen or changed. The administrator account is approved from the start and is signed in at once. Without `PLUGGED_ADMIN_EMAIL` the page says how to set it and nobody can sign in.
- **Wrong passwords**: after `PLUGGED_MAX_FAILED_LOGINS` wrong passwords in a row an account is locked for `PLUGGED_LOCKOUT`, also for the right password; an address without an account answers the same way, so the answers do not tell which addresses have an account. *Account → Gebruikers* shows 🔒 *Vergrendeld* and an *Ontgrendelen* button. A successful sign-in forgets the earlier wrong attempts.
- **Registering**: the sign-in page links to *Registreren* (`/#register`): first name, surname, email address and password (at least 8 characters). A new account is **not approved** and cannot sign in until the administrator approves it.
- **Account** is one item in the top bar for every user and opens a page (not a dialog). Everyone gets *Mijn account* there: change the password, download the own data, remove the own account. An administrator gets the same page as *Account en beheer*, with the tabs *Gebruikers*, *Groepen* and *Symbolen* next to *Mijn account*; only he sees all users and the standard symbols, and the requests behind those tabs are only made for him (the server refuses them for anyone else anyway). A badge on Account counts the accounts waiting for approval, and the page then opens on *Gebruikers*.
  - *Gebruikers*: *Goedkeuren* approves an account; *Maak beheerder* makes an approved account an administrator, *Maak gewone gebruiker* takes the role away again; *Weigeren* / *Verwijderen* removes an ordinary account. The primary administrator (the account of `PLUGGED_ADMIN_EMAIL`) always stays administrator, nobody takes the role away from himself, and an administrator cannot be removed (make him an ordinary user first). A change of role applies on the next request of that user, without signing in again; a removed account is signed out on its next request and its projects go to the administrator who removed it.
  - *Groepen*: create, rename and remove groups and choose their members (approved accounts). A user can be in several groups. Only administrators manage groups. ☆/★ on a member makes him an **owner** of the group (a teacher), and every group has the switch of its educational mode.
  - *Symbolen*: the standard symbols for the next release (see Components).
- **Educational mode** (per group, off by default): the members of the group who are not its owner (students) cannot validate a schema (no ✖/⚠ counts, no *Controleer* button or panel; on the situatieschema the elements still to place are a plain list without warning, title or counts, and the tab shows no ⚠ count) and cannot import or export a project (JSON or EDS), in *any* of their projects, so they cannot copy the work into a project of their own or into another installation of Plugged. PDF and print stay. Owners and administrators are never restricted; somebody who owns one group but is a student in another group in educational mode is restricted. The owners of a group (who are no administrator) get **🎓 Mijn groepen** in the top bar, where they switch the mode of their groups; administrators switch it under Account → Groepen. A student's editor fetches his status again when the window gets the focus and every minute, so a switch reaches students who are working; a student sees 🎓 in the top bar (*Educatieve modus* on mouse-over). The server enforces what it can: a student cannot create a project that already has content (`POST /api/projects` with circuits or anything drawn answers 403), which is what an import or a copy of somebody else's project would be; his editor creates a new project empty and then saves his work in it. A student can still read the projects he may open (the editor needs them), so with the developer tools of his browser he can copy what he sees into a project of his own.
- **Automatic save**: an own project that is already on the server (it has a number) is saved by itself, but sparingly so the database and the connection are not worn out (`hooks/useAutoSave.js`): only when something changed since the last save, 20 s after the last change (`AUTO_SAVE_IDLE`), and while you keep editing at the latest 2 minutes after the first unsaved change (`AUTO_SAVE_MAX_WAIT`); also right away when the tab is hidden or the page closed (a `keepalive` request, for documents under 60 KB). A failed save is tried again after 30 s, 1, 2 and then every 5 minutes, not with every change. The top bar shows *Automatisch opgeslagen om hh:mm*. A new project gets its number from a save by hand first, and a project of somebody else (shared with a group, or opened by the Hoofdbeheerder) is only saved by hand, so two people with the same project open never overwrite each other's work without noticing.
- **Mijn account** (👤 *Account* in the top bar): change the own password (the current one confirms it; every other session of the account is signed out), download *Mijn gegevens* (GDPR: the account, its groups, its projects with their documents, also those in the trash, and its own symbols, as one JSON file; no password), and remove the own account with everything that is his (his projects, also shared ones and those in the trash, with their history; his own symbols, which projects of others keep as their copy). The primary administrator cannot remove his account.
- **Temporary password**: the app sends no mail, so an administrator who is asked for a new password gives the account a temporary one under *Account → Gebruikers* (🔑 *Wachtwoord*). It is shown once, to pass on; the account is signed out everywhere and has to choose its own password at its next sign-in (until then the rest of the API answers 403). Not for the own account, and nobody but the primary administrator himself for the primary administrator.
- **Signing out**: *Afmelden* in the top bar (it asks first when the open project has unsaved changes). When a session ends during the work (timeout, restart of the server), the sign-in form opens on top of the editor, so the open project is not lost.
- **Projects and sharing**: every project has an owner, the user who saved it first. A user sees his own projects and the projects shared with one of his groups. The main administrator (the *Hoofdbeheerder*, `PLUGGED_ADMIN_EMAIL`) sees all projects of everyone, shared or not, and can open, save, share and delete them; other administrators manage users, groups and symbols, but for projects they are users like any other (`ProjectService`). In *Project → Laden* the owner (or an administrator) shares a project with groups (the 👥 button) and deletes it; members of those groups can open and save it, but not delete or share it. The list shows under each name whose project it is and who it is shared with. The server gives new projects their number (`POST /api/projects`, a database sequence; a client cannot choose one), so two users never pick the same one; the editor opens with the user's most recently saved project, or a new one. Projects saved before accounts existed belong to the primary administrator.
- **Versions**: every save of a project is a new version. The editor sends the version it loaded with each save (`If-Match`); when somebody else saved the project in between, the save is refused (409) and the top bar says so, instead of overwriting that work. Sharing a project is not a new version. The server only stores documents the editor can open (valid JSON, the expected parts of the expected kind; 400 otherwise).
- **History**: the newest `PLUGGED_PROJECT_HISTORY` versions of every project are kept, with who saved them and when. In *Project → Laden* the 🕘 button of a project lists them; *Herstellen* saves an older version again as the newest one (the current one stays in the history). Whoever may save a project may restore.
- **Duplicate**: the copy button of a project in the list makes a copy as a new own project ("... (kopie)"), not shared and without history. A student only duplicates his own projects.
- **Trash**: deleting a project puts it in the trash (*Prullenbak* in the list): its owner (or the primary administrator) restores it or removes it for good. After `PLUGGED_TRASH_DAYS` days it is removed by itself (every night). A project in the trash is not listed, opened or saved.
- **Search and order**: the list of projects is searched by name, number, owner and group (every word typed must match) and sorted by last save, name, owner or number.
- **Working together**: while a stored project is open, the editor reports itself every 10 s (`hooks/usePresence.js`). The top bar shows 👥 who else has it open (orange: somebody there has unsaved changes). When somebody else saves it and nothing is unsaved here, the newer version is loaded at once, on the same tab and page, so you follow along within seconds of every save; with unsaved changes here it is offered (*Laden*) instead. Closing the project or the window tells the server at once (a keepalive `DELETE`, so the others see it at their next heartbeat); every presence message of a window carries a rising number (`seq`), so a heartbeat that was still on its way and arrives after the leave is ignored instead of showing the window again for the whole timeout. This is not simultaneous editing: two people changing the same project at the same moment still meet the version check, and the second save is refused. Automatic saving stays for own projects only; somebody else's project is saved by hand (Alt+S).
- **Symbols**: the standard symbols are shared by everybody and changed (edited, deleted, restored, *Maak standaard*) by administrators only; for the others they are read-only in *Componenten*, where *Dupliceer* makes an own copy. An own symbol belongs to the user who made it, who shares it with any number of his groups (*Gedeeld met*, checkboxes; none = only he uses it), like a project: the members of those groups use it, members who are no students in educational mode can also improve the drawing, and only the owner (or an administrator) changes the groups or deletes it. Students share no symbols. A stored project carries a copy of the own symbols it uses (`symbols`), so it still draws for somebody it is shared with who does not have them. The symbols of a removed account go to the administrator who removed it; a removed group just no longer shares its symbols; own symbols from before symbols had owners belong to the primary administrator.
- Accounts live in the `users` table (name, surname, email, bcrypt password hash, `admin` default false, `approved`, and as telemetry `last_login` and `login_count`: when the account last signed in and how many times; the first start of the administrator counts as a sign-in). *Account → Gebruikers* shows them in the column *Laatst aangemeld*. Email addresses are stored in lower case.

REST API:
- `GET /api/auth/status`, `POST /api/auth/setup {name, surname, password, setupKey} | register | login | logout` (login: 401 wrong address or password, 403 not approved yet, 423 locked; 429 too many attempts from one address)
- projects: `GET /api/projects`, `GET /api/projects/summaries` (`{id, name, updated, owner, groups, mine, canManage}`), `POST /api/projects?name=` (answers `{id, version}`), `GET /api/projects/{id}` (version in the `ETag` header), `PUT /api/projects/{id}` (needs `If-Match: "<version>"`: 428 without it, 409 when it is outdated; answers the new `ETag`), `DELETE /api/projects/{id}`, `PUT /api/projects/{id}/groups {groupIds}`; a project the user may not see answers 404

- `GET /api/groups`: the groups the user can share with (his own; every group for an administrator); `GET /api/groups/owned`: the groups whose educational mode he may switch (with their members); `PUT /api/groups/{id}/educational {educational}` (an owner of the group or an administrator). `GET /api/auth/status` tells the editor `user.restricted` (a student in educational mode) and `user.ownedGroups`
- own account: `PUT /api/auth/password {currentPassword, newPassword}`, `GET /api/account/export` (a JSON file), `DELETE /api/account {password}`
- history, copies, trash and presence: `GET /api/projects/{id}/versions`, `GET /api/projects/{id}/versions/{version}`, `POST /api/projects/{id}/versions/{version}/restore`, `POST /api/projects/{id}/copy?name=`, `GET /api/projects/trash`, `POST /api/projects/{id}/untrash`, `DELETE /api/projects/trash/{id}` (`DELETE /api/projects/{id}` puts it in the trash), `POST /api/projects/{id}/presence {window, editing}` (answers `{others, version, savedBy, savedByMe}`), `DELETE /api/projects/{id}/presence?window=`

Everything under `/api/` needs a signed-in user (401 otherwise), except `/api/auth/**`, `/api/info` and `GET /api/public/**` (what the page of a QR code needs, see *QR code* under Features).

## Features
- **Eendraadschema**: multi-sheet A4 diagram with a bus, kWh meter, main differential and circuits; palette, properties panel and a collapsible tree (*Opbouw*).
- **Situatieschema**: floor plan with walls, rooms, doors/windows, dimensions and the symbols of the eendraadschema.
- **Bedradingsschema** (wiring diagram): a free technical drawing of how the wires run (see below).
- **Components**: the symbol library and a symbol editor.
- **Controleer**: verification against the AREI (Boek 1, version 07), each message with its article; see Verification below.
- **Export**: vector PDF (jsPDF + svg2pdf.js, A4 landscape, all sheets) and printing, both in the **Project** menu (*PDF downloaden*, *Afdrukken* or Alt+P), not in the top bar.
- **All sheets as SVG or PNG** (Project → Exporteren, next to .json and .eds; `features/project/pagesExport.js`): a zip file named after the title of the kader (`Villa-svg.zip`, `Villa-png.zip`) with one file per sheet, in the order of the PDF (`01 Eendraadschema - Hoofd.svg`, `02 Situatieschema - Gelijkvloers.svg`, ...; a page that takes several sheets gets (1), (2), ...), made in the browser with fflate. The sheets are rendered off screen as for the PDF and copied as standalone SVG, with the styles the stylesheets give them written on the elements (so e.g. the transparent click areas of the kader stay transparent).
  - *SVG*: a vector drawing of the sheet, A4 landscape in millimetres (`width="297mm" height="210mm"`, `viewBox="0 0 297 210"`), with its texts as text; it needs nothing of Plugged, to edit further in e.g. Inkscape or Illustrator.
  - *PNG*: a picture of the sheet, A4 landscape at 150 dpi (1754 × 1240 pixels) on white, drawn on a canvas from the same SVG.
  - Neither can be imported again. Like the other exports they are locked for a student in educational mode.
- **QR code** (Project → *QR-code*, **Alt+Q**, `QrDialog.jsx`, `schemaLink.js`): a QR code of a stored project to print and stick on the circuit board. The same code is made for any project from the list of **Project → Laden**: the QR icon behind a project opens the dialog for that project without opening it (the menu item and Alt+Q are for the open project, and need a saved project: the code refers to its number). The dialog shows only the code (the link itself is not written on the page); it prints the code with the name and number of the project (`print.css`) or downloads it as an SVG file (4 mm per module, with the quiet zone). The code holds `/?schema=<project number>&key=<secret>`, not the PDF, so it stays valid when the schema changes: whoever scans it, without an account, gets `SchemaPdfPage.jsx` with the newest saved version of the project, which can be shown, downloaded as PDF or printed. The secret (256 random bits, kept in the project) is made the first time the dialog asks for it (`GET /api/projects/{id}/qr-key`, any project the user may open); *Nieuwe sleutel* (`POST /api/projects/{id}/qr-key`, owner or primary administrator only) replaces it, after which the printed codes stop working. The public page reads `GET /api/public/schemas/{id}` with the secret in the `X-Schema-Key` header and `GET /api/public/symbols` (read only, never cached; a wrong or missing key, a project in the trash and an unknown project all answer 404, so nothing tells them apart). Not locked in educational mode. The link in the code is built from the address the editor is open on (`window.location`), so a code made on `localhost` or a local network address only works there: make the codes through the public address of the installation. The Info tab explains the code in plain words (*Over*, the *QR-code* step of *Gebruik* and three questions in the FAQ), and the guided tour shows it near the end.
- **Materiaallijst** (Project → Materiaallijst, `MaterialsDialog.jsx`, counted in `model/materials.js`): the bill of materials of the eendraadschema (all pages; the situatieschema does not count, it shows the same elements). Four sections: *Beveiliging* (main switch or main differential of the connection, the breakers / differentials / RCBOs of the circuits and separate differential and fuse elements, one line per article: kind, poles, rating and curve, sensitivity, type, breaking capacity, with the circuits that use it), *Kabels* (per cable designation with its circuits and their total length: typed in the circuit or estimated from the situatieschema, shown with ≈; `+ ?` when a circuit on it has no length, to fill in), *Toestellen en elementen* (per symbol with its *Aantal*, splash-proof separately, and the number of socket outlets) and *Borden*. Download as Excel (`.xlsx`, written in `materialsExport.js`: no library besides fflate for the zip) or CSV (`;` and a byte order mark, so Excel in a Belgian locale opens it in columns). Not locked in educational mode: it is not the project.
- **Metingen voor de keuring** (Kaderinfo): earth resistance (Ω), insulation resistance (MΩ) and the date of the measurement, stored in `project.footer` (`aardingsweerstand`, `isolatieweerstand`, `meetdatum`). They are always in the title block of every sheet (lower row: Ra and Riso under the address, the date under the owner; click one to edit it): a value that is not filled in yet is a dotted line, so the inspector can write it on the printed schema by hand. A filled-in earth resistance is also written under the earth symbol of the eendraadschema (`Ra = 24 Ω`).
- **Kabelberekening** (Eigenschappen of a circuit, `CircuitCalculation.jsx`, worked out in `model/calculations.js`): the cable length, typed in the field *Kabellengte (m)* (`p.lengte`) or, when empty, estimated from the situatieschema: from the board symbol (the one linked to the board, or a loose board symbol) to the nearest point of the circuit, then the nearest next, measured along the walls (horizontal plus vertical, not straight across the room), plus 1.5 m down and up in the wall at the board and at every point and 3 m for every change of floor (another plan page), rounded up to 0.5 m. Symbols that are not placed do not count. With the rating and the cable section it shows:
  - the voltage drop at the rated current (single phase 2·ρ·L·I / S on 230 V; three phase √3·ρ·L·I / S on 400 V when the circuit has 3 or 4 poles and the *stelsel* says 400 V), against the guideline of 3 % for lighting and 5 % for other circuits (the AREI sets no maximum);
  - the smallest short-circuit current at the end of the cable, 0.95 · 230 V / (Z network + 2·ρ·L / S), against what makes the breaker trip magnetically for sure (5 In for curve B, 10 In for C, 20 In for D);
  - the maximum length for that breaker and section.
  ρ is 0.0225 Ω·mm²/m (copper when warm). The impedance of the network up to the board is the field *Netimpedantie aan het bord (Ω)* in Kaderinfo (Ω, measured), else 0.3 Ω, and the panel says which one it used. All values are indicative and say so: they replace neither a calculation note nor the measurements. The length is written after the cable on the eendraadschema (`XVB 3G2,5 · ≈ 14,5 m`), and Controleer warns when the drop is too high or the breaker would not trip (rules *kring.voltageDrop* and *kring.shortCircuit*, which a user can switch off). There is no simulation of the circuit: what a switch does is what the drawing says.
- **Room names and areas** (`model/rooms.js`): the walls of a plan make rooms (closed areas between walls, split where walls cross or meet in a T; walls that end inside a room split nothing). A text on the plan with *Oppervlakte van de kamer eronder* on shows the area of the room it stands in under it (`5,00 m²`, following the scale); the room labels of the templates have it on. A symbol stands in the room whose name is written in it, so a circuit knows its rooms: a new circuit made with *Eendraadschema maken* gets them as its name (*tekst*), and the Eigenschappen of a circuit offer a button to take them over.
- **Recently used** symbols (situatieschema and bedradingsschema each their own, the last 8, kept in the browser): a row of icons above the palette, hidden while searching.
- **Undo/redo** (100 steps), **EDS import and export** with the online eendraadschema tool.
- **Languages**: Dutch, French and English (picker in the top bar).

## Eendraadschema layout and editing
- The diagram is drawn like the original tool: a horizontal bus with the kWh meter, main differential and earth below it, and circuits placed from left to right. Each circuit gets the width its elements need; a circuit that is lower than the overhang of the previous circuits slides left underneath it to save width and sheets. When a sheet is full the next circuits continue on the next A4 sheet ("vervolg op blad N"). Printed sheets stay readable: the drawing is never smaller than full size (`MM_PER_UNIT` = 0.17 mm per unit, at which its smallest text, 13 units, is as large as the titles of the footer, 2.2 mm). A circuit with the maximum of 8 points always fits on a sheet at that size, also with a name and a count on every point (a test checks every symbol of the library): the bus lies around the middle of the page while the circuits are low and goes down as points are added, to just above the footer (the head below it stays within `HEAD_DEPTH`, `busPosition`), and the specs, short-circuit rating and cable stand next to each other along the stem from just above the bus. Only a circuit with more points than fit with the bus at its lowest bends: the line goes over the top into a next column, where the points go up again from the bottom and the numbering carries on. A circuit with sub boards (or domotics boxes) in it that is too wide for one sheet is cut into parts on next sheets (`splitWide` in `model/boardLayout.js`): the parts are filled from left to right, a sub board with only plain circuits stays whole on one part, and every part repeats the way down to what it holds (the circuit and its breakers, and the boards it hangs in, each with only the circuits of that part); the connection and main protection are under the bus of every sheet. Sub boards in sub boards are higher than a sheet at full size and drawn smaller, but never below `NESTED_MIN_SCALE` (still readable on paper): a circuit inside a sub board whose points would need more height bends into a next column as well. Only something that does not fit even then (many detail lines under the points) makes its sheet smaller.
- New projects start with an aansluiting (kWh meter, 4P 40A 300 mA differential) and a geaard verdeelbord. Choose "Kring (automaat)" in the palette to append a circuit; elements are added to the selected circuit (or to the last one).
- **Palette**: click a symbol to add it, or drag it onto the diagram; a blue preview shows where it will land. Drag & drop never checks whether a symbol "fits": every symbol can be dropped anywhere and you correct a mistake afterwards.
  - A click adds under the selected element when it may hang there, else under the last element it may hang under. A *Kring* comes next in line: right after the circuit of the selected element (on the same board), or with nothing (or the board) selected as the last circuit of the board; a *Differentieel* the same way as a circuit protected by a differentieel (with a circuit selected it lies on that circuit's line). The new element is selected and the drawing scrolls to it, also when it lands on another sheet (the end of a long bus).
  - Over a symbol of a circuit: before it (left half) or after it (right half).
  - Over a circuit (its free area or stem): a *Kring* or *Differentieel* comes left or right of it, a smeltveiligheid in front of it, a *Verdeelbord* becomes the sub board (*Onderbord*) that circuit feeds, a teller / hoofdschakelaar goes on the main line, anything else becomes its last branch.
  - Over a sub board (*Onderbord*, its box or the board drawn with its circuits): a *Kring* or *Differentieel* becomes its last circuit (not a circuit next to the one that feeds it, nor on the main bus). A differentieel that feeds a sub board (as an EDS file gives it) counts as a circuit: dropping next to its stem puts the new circuit next to it.
  - Over the bus, the head or below the bus: a *Kring* or *Differentieel* becomes the last circuit, a teller / hoofdschakelaar in front of the board (on the main line), anything else under the board.
  - Anywhere else above the bus: the nearest circuit counts (a *Verdeelbord* then goes on the main line: only right on a circuit it becomes its sub board). Elements that are not drawn themselves show their place by marking the bus or the circuit in blue.
  - A *Differentieel* from the palette (dropped, or clicked while a board or nothing is selected) is a circuit protected by a differentieel: a *Kring* with *Bescherming* differentieel, 2P 25A 30 mA type A. It is drawn with the differentieel symbol and its specs (Δ30mA, 2P - 25A, Type A), like a differentieel from an EDS file, and a board dropped on it (or clicked while it is selected) hangs under it as its *Onderbord*. Clicked while a circuit is selected, a Differentieel stays a differentieel lying on that circuit's line.
- **Eigenschappen** (above *Opbouw*, close with the cross) holds the properties of the selected element. The toolbar there inserts an empty element before / after / as a branch of the selection (its Type dropdown only lists what fits there), moves it earlier / later, one level up / down, duplicates, deletes, and rotates a symbol counter-clockwise / clockwise in steps of 15° (full 360°).
- **Opbouw** shows the tree; main levels have an arrow that collapses / expands everything below them.
- **EDS ↓** in the header imports a file: the circuits, elements and owner/address for the footer. The situatieschema in the file is not imported (existing situatieschema pages and walls are kept and their symbols are cleared). Unknown element types become "Vrij element"; the import message lists them. A differential circuit of the file (protection "differentieel" or "differentieelautomaat") that feeds a board is imported as a *Differentieel* (specs such as `4P 40A 30mA type A` in its info) with the board as an *Onderbord* under it, and is drawn as the circuit of that board. A circuit or differentieel directly under another one (e.g. a second breaker in front of a sub board) is drawn as a breaker lying on the line, with its name above and its specs under it. Circuits inside a sub board are drawn exactly like the circuits on the bus (breaker, specs, short-circuit value, plaatsing, in buis, numbers of the elements) and are selected the same way, by clicking anywhere on their stem. A Differentieel may hang under a Differentieel, Kring, Overspanningsbeveiliging or Onderbord.
- **EDS ↑** exports the eendraadschema (all sheets one after the other) and the owner/address as a `.eds` file that the online tool opens. The situatieschema is not exported. A Differentieel that feeds boards is written back as a differential circuit; meter, main switch and the other differentials are part of the Aansluiting in the EDS format; symbols without an EDS equivalent (own components, fridge, buzzer, ...) are written as a free consumer named after the symbol, and the export message lists them.

## Bedradingsschema (wiring diagram)
- The third tab, after the situatieschema: a free drawing of how the wires run, e.g. the wiring of a board, a control circuit with contactors, push buttons and an emergency stop, or the cable runs on a floor plan. It is the editor of the situatieschema (`SituationSchema.jsx` with `listKey="wire"`, ids start with `wire-`): grid, free drawing, zoom, scale, walls, rooms, doors, windows, symbols and text work the same; it has no *Nergens geplaatst* list and no templates. Its pages are `project.wire` (`{id, name, walls, items, wires, boxes, dims}`, model in `model/wiring.js`; older projects get one empty page when they are opened).
- **Draad** (wire): click a connection point of a symbol (the blue dots shown while the tool is on) or the grid, click to bend, and click a connection point or another wire to end (a double click, a right click or Enter ends at the last point; Escape drops the wire). An end on a symbol is stored as `{item, pin}` and follows the symbol when it moves or turns; an end on another wire makes a branch and a **junction dot** (where three or more wires meet at a free point). *Rechte hoeken* (on by default) draws the wire with right angles. Deleting a symbol leaves its wires with a free end where they were; copying symbols with their wires keeps them attached.
- **Kader** (frame): a rectangle in two clicks, e.g. the enclosure of a board.
- **Line style** of a wire or frame (*Lijnstijl*, for the next one while the tool is on, or for the selected one): solid, dashed, dotted or dash-dot; black, grey, brown, blue, red, green or green-yellow (earth, drawn with yellow dashes); 0.25 to 1 mm. The lengths of the wires show with *Maten* (off by default on this tab).
- **Symbols**: the standard catalog has the symbols of IEC 60617 (keys `iec_<page>_<row>` after the rows of the IEC 60617 symbol list, about 495 of them, plus stay-put variants (`_v`, the detent V in the linkage), the crossover contacts of a kruisschakelaar (`iec_22_11_kruis`) and a thermal-magnetic circuit breaker (`iec_14_09_mcb`)), only on the bedradingsschema (`een: false`, `wire: true`), in categories such as *Contacten & schakelaars*, *Bediening & mechanisch*, *Relais, spoelen & starters*, *Beveiliging*, *Machines*, *Transformatoren*, *Halfgeleiders*; rows of the list that Plugged already had (the contacts, push buttons, coil, thermal relay, fuse, lamp, terminals, the installation symbols of AREI) use that symbol. The palette of the bedradingsschema folds per category (`details.palgroup`, ids `comp-category-<category>`): the contacts open, all of them while searching. The emergency stop is drawn latching with positive opening. Also *Inrichting* (toilet, washbasin, shower, bathtub, bed, table, sofa, kitchen counter, cupboard, car; also on the situatieschema). Symbols can be made much larger here (up to 150 mm). **Plattegrond overnemen** copies a page of the situatieschema (walls, doors, windows, texts and, if wanted, its symbols as loose symbols with their marking).
- **Symbol settings** (Componenten): *In het palet van het eendraadschema* (`een`, default yes), *In het palet van het bedradingsschema* (`wire`, default: when placeable) and the **Aansluitpunten** (`pins`, `[[x, y]]` on the 24 grid): found from the drawing (the ends of lines on the border, else the centre) or set with the *Aansluitpunten* tool; *Geen* for furniture. The backend stores them (`in_een`, `in_wire`, `pins` "x,y;x,y") and checks them (at most 60, on the grid); `StandardSymbols.VERSION` 15.
- Printed (PDF, print, SVG/PNG export, QR page) after the situatieschema; an empty page is left out.

## Situatieschema and bedradingsschema: the tool rail
- The tools are a narrow dark column of icons on the drawing, top left (`features/situation/ToolRail.jsx`, ids `sit-tools` / `wire-tools`, `<prefix>-tool-<tool>`): *Selecteer* and *Wis*, then *Muur*, *Kamer*, *Deur*, *Raam*, then *Symbool* and *Tekst*; the bedradingsschema adds *Draad* and *Kader* after *Wis*. The active tool is yellow. The last button (the house) is *Sjabloon* on the situatieschema and *Plattegrond overnemen* on the bedradingsschema.
- **Name and shortcut**: pointing at an icon (or keyboard focus) shows its name and its key. The keys are letters per language (`situation.toolKeys` in the translations; Dutch V Selecteer, M Muur, K Kamer, D Deur, A Raam, S Symbool, T Tekst, W Wis, L Draad, B Kader; English V W O D N S T E L F; French V M P O F S T E L C). A letter works with or without a selection, not with Ctrl/Alt/Cmd and not while typing in a field; R stays *turn the selection* (a unit test checks that the keys of a language differ from each other and from R). The Info page lists them from the same texts.
- **Fold**: the arrow at the top folds the rail to one button that shows the active tool (the keys keep working); the choice is remembered in the browser (`plugged.toolRailFolded`) for both tabs.
- **Help**: one line of help for the active tool sits bottom left on the drawing (`<prefix>-help`, clicks go through it); it is hidden while the rail is folded, while the box for a typed length is open and on a narrow screen.
- The left side keeps the properties of the selection and the components, whose list takes all the height that is left down to the bottom of the window.

## Situatieschema: starter templates
- **Sjabloon** (the house at the bottom of the tool rail, or the yellow banner on an empty sheet) opens a choice of floor plans to start from: *Studio* (6 × 5.4 m), *Appartement* (12 × 8.5 m, two bedrooms), *Rijwoning* (10 × 6 m, ground and first floor) and *Vrijstaande woning* (12 × 8 m, ground and first floor). Each card shows a small preview of every floor, the size, and the scale it will be drawn at.
- What it inserts is an ordinary drawing: walls (shared walls are one line), doors, windows and the room names as texts, all to edit, move or delete as usual; one undo step takes it all away. A template with two floors gives two sheets.
- **Where**: on an empty sheet the (first) floor goes on that sheet and the other floors on new sheets right after it; on a sheet that already has a drawing every floor gets a new sheet after the current one. Nothing that is already drawn is changed.
- **Scale**: while nothing is drawn yet (situatieschema and bedradingsschema), a template is drawn as large as the sheet allows: at the first standard scale it fits at (1:20, 1:25, 1:40, 1:50 … 1:200), so the studio and the terraced house at 1:40, the apartment and the detached house at 1:50, and the kader is set to that scale (also when the project had 1:75). Once something is drawn the scale of the project stays (lengths on the drawing would change): the template is drawn at that scale when it fits, otherwise the card says so and its button is disabled.
- **Adding a template**: `model/planTemplates.js`. A template is a list of floors in metres (rooms as rectangles, doors and windows on a wall, `passages` for an opening without a door such as a staircase onto the hall); its name, description, floor and room names are in the `templates` block of the translations. `test/model/planTemplates.test.js` checks every template (rooms inside the outline and not overlapping, every opening on a wall, every room reachable, stairs in the same place on every floor, all names translated).

## Situatieschema: placing symbols
- The left list holds the components that can be placed; filter it with the search box. The *Nergens geplaatst* panel right of the drawing lists the eendraadschema elements that are not on the plan yet; collapse it with the `>` button above it (in the line of the page buttons, at the right): collapsed it takes no room at all, and the drawing takes its width.
- The marking of a placed symbol (its circuit and number, e.g. A1, F5) is written on the first free spot around the symbol: right (the default), then top-right, bottom-right, left, top-left, bottom-left, above and below. A spot is free when it does not touch a wall, another symbol, a door, a window, a text, the length of a wall or the marking of another symbol, and stays on the drawing area; when no spot is free the one that hides the least wins. It is recalculated on every change, so moving a symbol or placing one next to it moves the marking along (model/labelPlacement.js; the PDF uses the same placement). The marking is written right next to the lines of the symbol (the box around its lines, turned with it), not next to the square the symbol is drawn in, so it stays close to a narrow symbol such as a bell. It grows and shrinks with the size of its symbol (2.6 mm at the standard size 7), but never below 2.2 mm, the size of the titles of the kader, so a print stays readable.
- **Eigenschappen** of the selection (a symbol, text, door or window; a wall; several elements) look the same as on the eendraadschema (`components/PropertiesBox.jsx`): a heading with a close button at the top right, what is selected, the fields, and a row of icon buttons with a hover text: turn 15° either way and 90°, mirror (doors and windows), duplicate and delete.

## Screen sizes
- **Panels as high as the window**: the palette and *Opbouw* of the eendraadschema, the components and the *Nergens geplaatst* list of the situatieschema and bedradingsschema and the list of Componenten reach exactly to the bottom of the window, whatever its size (`hooks/useFillHeight.js` sets their height from their top to the bottom of the window and follows scrolling and resizing). The part marked `fill-grow` (Opbouw, the component lists) takes the room that is left and scrolls inside; when even that does not fit, the whole panel scrolls.
- **The situatieschema** takes all the width between the panels; collapsing *Nergens geplaatst* gives it that width too. A sheet that is higher than the window scrolls with the page, the panels stay in view.
- **Laptop** (up to 1500 px wide): Ongedaan, Opnieuw, Info, Account and Afmelden in the top bar show only their icon (their text is the hover text), so the bar keeps one line.
- **Tablet upright and phone** (up to 900 px wide, `NARROW_SCREEN`): the panels stand above the drawing (at most 45% of the screen high, scrolling inside) and *Nergens geplaatst* below it, with words on its toggle; Ongedaan, Opnieuw and Kaderinfo show only their icon too; the *Eigenschappen* of the selection sit along the bottom of the screen, over the drawing, always in reach; dialogs take the width of the screen; the mouse and keyboard help of the situatieschema is hidden. Tapping works like clicking everywhere; dragging from the palette of the eendraadschema needs a mouse, a tap on a symbol adds it as well. The symbol editor (Componenten) can be used with taps, but drawing a selection box needs a mouse.
- **Fingers** (a tablet, checked on 10" sizes in both orientations by `e2e/tablet.spec.js`): one finger draws, selects and drags (the drawing has `touch-action: none`, so a finger on it never scrolls the page); **two fingers pan** the zoomed drawing and **pinch** steps through the zoom levels around the point between them (`components/ZoomPane.jsx`), and a two-finger gesture never draws. The tool rail, the zoom buttons and the grid choice take a finger like the drawing, the page has `overscroll-behavior: none` (a swipe never goes back in the history or reloads the page with pull-to-refresh, which would lose a drawing that is not saved), and every control has `touch-action: manipulation` (a tap acts at once, without waiting for a double tap). While the *Eigenschappen* lie along the bottom of a narrow screen, the page can scroll that much further, so *Nergens geplaatst* never stays hidden under them. A tap on a tool shows its name and help next to the rail, as pointing at it does with a mouse.

## Situatieschema drawing
- Drawing and dragging snap to the grid points (grid size selectable bottom right; a blue marker shows the snapped point, with a preview for walls and rooms). Tick **Vrij tekenen** (bottom right, off by default) to draw at any position.
- Zoom with the − / % / + buttons in the top right of the drawing (50%–400%); click the percentage to reset.
- **Eendraadschema maken** (`model/generateOneWire.js`, the box at the top of *Nergens geplaatst*): starting from the plan, the loose symbols of all plans (drawn from the palette, not yet an element of the eendraadschema) become circuits by their text: `B4` is point 4 of circuit B, and everything with the same text is that one point: its switches in series and the lamp(s) under the last switch (`wissel → wissel → lichtpunt`). A circuit with only lamps and their switches gets 16 A with XVB Cca 3G1,5, any other one 20 A with XVB Cca 3G2,5 (2 poles, curve B, as a new circuit in the editor). A dialog (centred, the circuits as a table with a row each and a summary such as *24 kringen · 8 × 16 A · 16 × 20 A*) shows what will be made first; the breaker (6–40 A) and cable of every new circuit can still be changed there, the cable following the breaker (16 A 3G1,5, 20 A 3G2,5, 25 A 3G4, 32 A 3G6, 40 A 3G10) unless another cable was typed or picked. The symbols that are left out (no text like A1, or a point that is already in the eendraadschema) are grouped by kind, and *Toon op het plan* selects them (on their own plan). The new circuits come under the existing board (a project without one gets the connection and board of a new project); a letter that already is a circuit gets the new points at its end; nothing that exists changes. A point number that is not the position of the point is written on it (`p.nr`). Every symbol that became an element is linked to it (its text, type and waterproof property now come from the eendraadschema), and one *Ongedaan maken* takes it all back. Furniture and the parts of the board are not part of a circuit.

## Situatieschema: selecting, dimensions and layout
- **Right click** cancels what you are drawing and switches back to *Selecteer*.
- **Select**: click an element (hit areas are generous) or drag a box on an empty spot to select everything it touches; Shift adds/toggles. A selection moves (drag, arrow keys), rotates (R), duplicates and is deleted (Del or the trash button at the top right of the selection) as one group.
- **Dimensions**: lengths are shown along the walls, computed from the footer scale (`1:50` by default). The **Maten** button (top right of the drawing) shows/hides them; the setting is stored per sheet and also applies to PDF/print. While drawing a wall or room you can type its size and press Enter: `3,5` or `350cm` for a wall, `4x3,5` for a room (metres unless you add `cm`/`mm`); the direction follows the cursor. Selected walls and doors/windows have a length/width field.

## Components (symbol library)
- The **Components** tab has a menu with all components on the left and the selected component on the right: name, category, where it may hang, placeable on the situatieschema, and a 24x24 drawing canvas (line, circle, rectangle, half circle, text) with a **Raster** dropdown (0.5 / 1 / 2 / 4) that sets the grid and the snapping. The connection point of a symbol is the red centre line (y = 12).
- The symbols live in the backend, in the H2 database (tables `symbols`, `symbol_parents`, `symbol_shapes`; REST `/api/symbols`). The standard symbols that ship with the application are the **catalog file** `backend/src/main/resources/catalog/standard-symbols.json` (read by `StandardSymbols.java`). On every start, before the web server answers (`SymbolSeeder`), a new installation gets them, and an existing one replaces its stored standard symbols that nobody edited when their drawing differs from the catalog; edited ones are kept. Standard symbols can be edited and restored ("Standaard herstellen" per symbol, "Alle standaard herstellen" for all of them; they cannot be deleted); own symbols can be duplicated and deleted. The library is shared by all projects; own symbols are also written into the exported project JSON (`custom`).
- **Changing the standard symbols for a release** happens in the application: draw a standard symbol in the Components tab and choose **Maak standaard**, then **Account → Symbolen** lists what differs from the running version and downloads the complete catalog (`standard-symbols.json`, one symbol per line, so git shows readable differences). Replace the catalog file with it and build; `StandardSymbolsTest` checks the rules a catalog must follow (valid shapes, known parents, every circuit symbol touches `y = 12`, one arch per socket). Only "Maak standaard" counts: an edit that was not made the standard, a deleted standard symbol and the users' own symbols do not change the catalog. The download cleans up what would break the build: a parent that is a user's own symbol (`custom:…`) is left out, and socket properties a standard misses (an older database without the socket count `n`) come from the running catalog. Whatever still breaks one of the rules is listed in **Account → Symbolen** above the download, per symbol, so it can be fixed with "Maak standaard" or "Standaard herstellen" first. API: `GET /api/admin/symbols/catalog` (the file), `GET /api/admin/symbols/catalog/changes` and `GET /api/admin/symbols/catalog/problems`.
- Orientation: the eendraadschema chains the symbols along a horizontal line, so every symbol touches the line `y = 12`. Sockets are drawn rotated: the supply meets the apex of the arch. Shapes can be `line`, `circle`, `rect`, `arc`, `text` and `path` (SVG path data), with a relative line weight `sw`, white fill (`f: 2`) and bold text (`b`). Breakers and the earthing symbol are vertical symbols. A socket can still be drawn vertically (hanging) per element with the "Horizontaal" checkbox. A socket keeps the drawing of the catalog; a waterproof one (h) gets a little `h` above it. Only stacks (Aantal) and hanging sockets are computed, by `socketShapes` in `frontend/src/symbols/symbolShapes.js`, in the style of the double and triple socket of the catalog (`symbols.test.jsx` checks it): when you redraw those, change `socketShapes` too.
- API: `GET /api/symbols`, `GET /api/symbols/template`, `GET|PUT|DELETE /api/symbols/{k}` (400 when invalid, 409 when deleting a standard symbol), `POST /api/symbols/{k}/restore`, `POST /api/symbols/restore`.
- The frontend tests (`src/test/fixtures/standardSymbols.js`) and the fake backend of the browser tests read the same catalog file as their library, so they always test the symbols that ship; there is no copy to keep in step.

Not checked, because the drawing does not show it: which room a circuit feeds and the volumes around a bath or shower (bathrooms need 30 mA too, 7.1.4.3, and sockets and switches are limited per volume, 7.1.5), the name, capacity and VAT number of the installer (3.1.2.1 a: on the schema too, there is no field for it yet), the power of an appliance, embedded floor heating (its own differential of at most 100 mA). Cable lengths are typed or estimated (see Kabelberekening); without either the voltage drop and short circuit are not checked. Selectivity between differentials is only required for safety installations (5.5.7), so it is not a rule here.

A rule is left out for an installation that started before its date; when only a year or month is known that runs across the date, it is still reported with a note that it may not apply; an empty or unreadable field means a new installation (everything applies). The dates are in `RULE_CATALOG` (`since`) and on the Controleregels page:

| 01/06/2023 | sockets and lighting behind 30 mA (washing machine, dryer and dishwasher always); at most 8 circuits per 30 mA differential; above 30 Ω the other circuits behind at most 100 mA | 6.5.8.1, 1 |

**The Controleer panel** opens with how many checks are in order (*x van y controles in orde*), then *Vóór de keuring in te vullen*: what the inspector needs that is still missing in Kaderinfo (the fields of the title block, the measurements), each with a link that opens that field. The messages are grouped like the Controleregels (structure, differentials, earth, circuits, cables, ...), each group with its count of checks in order; a group with an error or a warning is open, a group without is closed and marked as in order.

An installation started before 01/06/2020, when Book 1 came into force, gets an info: Controleer checks Book 1, an old installation falls under the derogations of part 8. The Controleer panel says how many rules do not apply and links to the field.

**Controleregels** (Account → Controleregels, `features/account/RulesPanel.jsx`): every user switches rules off and on for himself; it applies to all his projects, and a rule that is off is left out of the list and the ✖ ⚠ counts (an empty schema is always reported). The rules come from `RULE_CATALOG` in `model/rules.js` (group, usual level, AREI article; names in `ruleSettings.rules.*`), and every change is saved at once: `GET /api/account/rules` answers `{disabled: [rule ids]}`, `PUT /api/account/rules {disabled}` sets them (400 `account.invalidRules` for an id that is not a rule id, or more than 200). They are stored in the table `user_disabled_rules`, are part of *Mijn gegevens downloaden* and go with the account. The Controleer panel says how many rules are off and links to the page. Every check goes through this catalog, also what the situatieschema shows: with *plan.unplaced* off the Situatieschema tab has no ⚠ count and the list of elements still to place is shown neutrally (as for a student in educational mode). A socket is any symbol with socket properties (`sock` in the catalog: `pe` earth contact, `kid` child-safe, `n` outlets), so a user's own socket symbol is checked like the standard ones and a multiple socket counts as one.

**Thema** (Account → Mijn account, `features/account/AccountPanel.jsx`): every user picks the colours of the interface: *Marine* (the default: navy bars with yellow accents), *Werkbank* (dark bars and panels; the sheet is the only light surface) or *Helder* (white bars, yellow only for what is active). The colours are CSS variables in `styles/theme.css`; `app/theme.js` puts the choice as `data-theme` on `<html>` and keeps a copy in the browser (`plugged.theme`), so the next visit starts in the right colours before signing in. `GET /api/account/theme` answers `{theme}` (marine when never chosen), `PUT /api/account/theme {theme}` stores it (400 `account.invalidTheme` for another name); it is part of *Mijn gegevens downloaden*. The drawings never use the theme: sheets, symbols, the title block, the PDF and printing stay black on white, and a symbol in a list gets a white tile on the dark theme. All interface icons are one family of line icons (`components/Icon.jsx`), not emoji.
The limits are in `LIMITS` in `model/rules.js`. A schema without errors is not an approved installation: the inspection by an accredited body decides.

## Guided tour
- A new visitor gets a short guided tour (`Tour.jsx`, steps in `tourSteps.jsx`, styles in `styles/tour.css`): a dimmed page with the next control highlighted and a card that explains it. The tour walks through the palette, a first *Kring* and its *Eigenschappen*, a stopcontact, then the situatieschema: a first wall (two clicks), a second wall with a typed length (the person has to type about 15 m, which is too long for the default scale 1:50, so the application proposes a scale and the tour has the person choose it and confirm the wall), the *Kaderinfo* where the scale is shown and can be changed, a door, a symbol, the *Nergens geplaatst* panel and the properties of a symbol. It ends with the **Project** menu and then, just before the last card, the **QR code for the circuit board** (step `qr`: what the code is for, that it always shows the latest saved version and that the project has to be saved first, with a small example code beside the text; the example holds the address of the application itself, never a schema). Steps that ask the person to do something wait until they did it; "Sla over" skips such a step.
- **First visit**: the browser remembers per user that the tour was seen, in `localStorage` (key `plugged.tour.<user id>`), so a new account that signs in on a browser where somebody else already saw the tour still gets it (`TOUR_VERSION` in `Tour.jsx` decides which version was seen, raise it to show a changed tour to everybody again). Without storage (private mode) the tour is shown once per page load. It starts when the project has been fetched, and only when that project is empty: a new browser that finds real work on the server does not get the tour by itself, so the tour cannot be saved over it.
- **Start it again** with **▶ Rondleiding starten** at the top of the **Info** tab (it asks first when the open project already contains work). The last step offers *Leeg project starten*, because the tour leaves a circuit, walls and a door in the open project.
- **Change the tour**: steps are data in `tourSteps.jsx` (`target`, `place`, `tab`, and `watch` for a step that waits for an action). Targets are `data-tour="..."` attributes in the editor (palette buttons are `pal-<symbol key>`, tools are `tool-<tool>`), so renaming classes or ids does not break the tour.
- Steps that watch the page itself (the typed length, the *Schaal* button, the Kaderinfo dialog) use a `watch` that reads the DOM; `tourSteps.test.jsx` tests those functions, including the values that must not finish a step.
- Tests: `features/tour/Tour.test.jsx` (the component), `features/tour/TourApp.test.jsx` (inside the real editor, every step must point at something that exists) and `e2e/tour.spec.js`. The other tests start as a visitor who has seen the tour (`src/test/setup.js`, `e2e/fixtures.js`).

## Shortcuts and editing

- **Ctrl/Cmd+Z**: undo, **Ctrl/Cmd+Y** or **Ctrl/Cmd+Shift+Z**: redo (also buttons in the header; changes made within 0.5 s, like typing or dragging, form one step).
- **R** (situatieschema): rotate the selection.
- **A letter** (situatieschema and bedradingsschema): choose a tool, see *the tool rail* above; the key shows when you point at a tool.
- **Project menu** (anywhere in the editor, `App.jsx`): **Alt+S** save, **Alt+N** new project, **Alt+L** open the menu with the list of projects, **Alt+I** import, **Alt+E** export (open or close the dialog), **Alt+Q** the QR code of the open project; the menu shows the keys next to its items. Alt and not Ctrl, because the browser keeps several Ctrl keys for itself (Ctrl+N a new window, Ctrl+L the address bar). Only Alt alone counts: Ctrl+Alt is AltGr on Windows (AltGr+E = €), and Shift or Cmd leave the key to the browser. On a Mac Option+letter types a special character, so there the physical key (`event.code`) counts, except in a text field, where Option+E is the accent of é. In educational mode Alt+I and Alt+E do nothing.
- **Footer**: click any cell of the footer on a sheet (or the yellow "Kaderinfo" button) to edit it.
- **Messages** (saved, loaded, failed, ...) appear as a toast at the bottom right (`components/Toast.jsx`) and fade out after 3 to 8 seconds, so the top bar keeps one row (down to about 1280 px wide; below 1500 px the minor buttons show only their icon). The toast never catches a click and is not printed.

## Languages
The application speaks Dutch (`nl`, the language the texts are written in), French (`fr`) and English (`en`, for a browser in any other language).
- **Frontend**: every text is in `frontend/src/i18n/locales/{nl,fr,en}.js`, one nested dictionary per language with exactly the same keys (a unit test checks the keys, lists and `{placeholders}`). Components use `const {t} = useTranslation()` and `t('pages.sheetName', {number: 2})`; plain modules import `t` from `i18n/translate.js`. Longer help texts use `RichText` (`**bold**`, `[[Ctrl]]` for a key, `\n` for a line break, a list = paragraphs). A text missing in French or English falls back on Dutch.
- **Choosing the language**: the stored choice (`localStorage['plugged.language']`), else the first browser language Plugged speaks (`nl-BE` → Dutch, `fr-CH` → French), else English (`DEFAULT_LANGUAGE`). The picker (`#language-select`) changes it at once and sets `<html lang>`.
- **What stays Dutch**: the stored project and symbol data (JSON keys such as `een`, `sit`, `footer.schaal`, symbol keys such as `stopcontact`) and the names of the standard symbols in the database, so existing projects, exports and `.eds` files keep working. The names of standard symbols and categories are translated when they are shown, as long as the user did not rename them. Default labels that the application generates (e.g. "Verdeelbord") are recognised in every language.
- **Backend**: every request carries `Accept-Language` (`api/http.js`). Error answers of the API are RFC 9457 problem details whose `detail` is written in that language (`backend/src/main/resources/i18n/messages*.properties`, `LocalizedStatusException`, `LocalizedExceptionHandler`, `LocaleConfig`); `messageKey` holds the language-independent key. Any other language (or none) gets English.
- **Adding a language**: copy `locales/en.js`, translate it, register it in `LANGUAGES`/`DICTIONARIES` of `i18n/translate.js`, add a `messages_xx.properties` and the locale to `LocaleConfig.SUPPORTED`.

## Test conventions
Tests find elements by their **id**, never by the text on a button: texts change with the language. Every interactive element has a stable id, prefixed by the part of the screen it belongs to (`tab-*`, `btn-*`, `eds-*` eendraadschema, `sit-*` situatieschema, `comp-*` symbol editor, `verify-*`, `footer-*`, `tour-*`, `project-*`, `export-*`, `auth-*` sign-in / registration / first start, `admin-*`, `users-*`, `group-*` Account page). Ids built from data go through `toDomId` (`custom:1` becomes `custom_1`), e.g. `#eds-palette-stopcontact`, `#eds-tree-<node id>`, `#comp-item-<symbol key>`. Where a test does check a text, it compares it with the dictionary (`t('app.saved')` in unit tests, `t()` of `e2e/texts.js` in Playwright), so a rewording of a text never breaks a test. Unit tests run in Dutch (`src/test/setup.js`), the browser tests in a Dutch browser (`locale: 'nl-BE'`); `i18n.test.jsx` and `e2e/i18n.spec.js` cover the switching.

## Build, tests and Docker
- `cd backend && mvn clean install` builds everything: it installs Node 22 locally (into `frontend/node`), runs `npm ci`, builds the React app into the jar, runs the backend tests **and the frontend tests** (`npm test`), then enforces the JaCoCo gate.
  - `-DskipTests` skips backend and frontend tests; `-Dfrontend.skip=true` skips Node, the frontend build and the frontend tests (the jar then has no UI).
- Frontend only: `cd frontend && npm test` (Vitest + React Testing Library, jsdom); `npm run coverage` enforces thresholds (95% lines/statements/functions, 90% branches).
- Backend only: `cd backend && mvn verify` (JUnit 5, Spring Boot Test, MockMvc, @DataJpaTest, JaCoCo with a 90% line gate; report in `target/site/jacoco`).
- **Logging during the tests** is off, so the output stays readable: the backend tests use `src/test/resources/logback-test.xml` (show the logs with `mvn test -Dplugged.test.log=DEBUG`), the application under Playwright gets `logging.threshold.console=OFF` from `frontend/e2e/application-test.properties` (show its log with `E2E_LOG=1`). The repository tests do not print SQL (`@DataJpaTest(showSql = false)`), and Mockito is loaded as a Java agent so the JDK does not warn about it. `logging.threshold.console` also works for the application itself (e.g. `--logging.threshold.console=WARN`).
- **Who did it**: every log line written during a request carries the signed-in user (his email address, `[-]` without one), e.g. `2026-11-04 15:11:18.509 INFO  [http-nio-8080-exec-4] [admin@example.be] c.p.p.c.AuthController : User 1 signed in (sign-in number 1)` (`logging/UserMdcFilter`, `%X{user}` in `logback-spring.xml`). A refused sign-in is logged with the address that was tried.
- Docker: `docker compose up --build`. Run the tests during the image build with `docker build --build-arg RUN_TESTS=true .`. Plain Docker: `docker build -t plugged . && docker run -p 8080:8080 -v plugged-data:/data plugged`. Extra JVM options: `-e JAVA_OPTS="-Xmx512m"`.
